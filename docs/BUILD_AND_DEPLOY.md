# Build, Deploy, and Operate Pirate

## 1. Reproducible Setup

Use Node **24.x**. The lockfile is authoritative for package versions. Do not install global `expo-cli`.

```bash
git clone https://github.com/dororolkp/pirate-native.git
cd pirate-native
node --version
npm --version
npm ci
npx expo-doctor
npm run check
```

- `npm ci` removes/replaces `node_modules` and installs pinned packages.
- `expo-doctor` checks app configuration and Expo/native dependency compatibility.
- `check` runs lint, source/test type checking, unit/adapter tests, and a web export.
- `package.json` declares Node 24 so cloud hosting selects a compatible runtime.
- Native project folders are generated by Expo Continuous Native Generation; they are not committed or edited manually.

Core versions at the visual-design release: Expo 58.0.26, React Native 0.88.1, React/React DOM 19.3.0, Expo Router 58.0.32, Expo FileSystem 58.0.14, React Native Web 0.21.4, SVG 15.16.0, AsyncStorage 2.2.0, TypeScript 6.0.3. Tooling and all transitive versions are in `package-lock.json`.

The portable lockfile was generated without an existing `node_modules` tree so platform-specific optional packages are present for Linux cloud builds as well as Windows. If regenerating it after an upgrade, use a clean checkout/directory; do not hide missing lock entries by changing production installation to `npm install`.

## 2. Environment Configuration

For demo mode leave `EXPO_PUBLIC_API_BASE_URL` empty or unset.

PowerShell:

```powershell
Copy-Item .env.example .env.local
notepad .env.local
npx expo start --clear
```

macOS/Linux:

```bash
cp .env.example .env.local
npx expo start --clear
```

`.env.local` values:

```dotenv
EXPO_PUBLIC_API_BASE_URL=https://approved-api.example
EXPO_PUBLIC_ROBOT_ID=robot_01
```

These are **public build-time values**. Changing them requires a new bundle/build/deployment. Authentication secrets, robot credentials, Expo tokens and store keys never belong in `EXPO_PUBLIC_*`, source code, or Git. `.env*` is ignored except the safe `.env.example`.

For EAS profiles configure the same non-secret values through the selected Expo build environment or profile `env` settings. Production defaults to a demo unless an API URL is supplied; verify the environment before shipping.

Settings also offers a validated **session-only** backend URL and an explicit Connect backend button. This does not modify build-time configuration or persist credentials/URLs. Use David's server base URL without `/api/v1`, with HTTPS and CORS for deployed web. His GitHub repository is not a hosted endpoint. See [Frontend Guide](FRONTEND_GUIDE.md) for mock-server setup and [ROS Backend Integration](ROS_BACKEND_INTEGRATION.md) for the verified payloads.

## 3. Web Development and Local Production

```bash
npm run web
```

Starts Expo/Metro with web support. For a production static site:

```bash
npm run build:web
npm run preview:web
```

`dist/` contains per-route static HTML, hashed bundles, favicon, robots rules and sitemap. `serve dist` serves clean URLs without SPA fallback. Stop the previous Metro server if port 8081 is occupied.

Do not open `dist/index.html` using `file://`; modules and routing need an HTTP server. This is a statically rendered Expo Router website with client hydration, not a Next.js/API server or offline-installed PWA. Local mission data is not embedded in static HTML.

## 4. Vercel Production Deployment

The delivery project is `pirate-native` in the authenticated Vercel workspace, linked to `dororolkp/pirate-native`.

### Dashboard

1. Import https://github.com/dororolkp/pirate-native into Vercel.
2. Framework preset: **Other**. Root directory: repository root.
3. Node.js: **24.x**. Install: `npm ci`. Build: `npm run build:web`. Output: `dist`.
4. Leave the API URL unset for the public safe demo.
5. Deploy and verify `/`, `/robots`, `/missions`, `/analytics`, `/settings`, including direct navigation and browser reload.
6. Confirm the Git default branch is the production branch. Pull requests get preview deployments if enabled.

### CLI

```bash
npx vercel@latest login
npx vercel@latest link --yes --project pirate-native
npm run check
npx vercel@latest deploy --prod --yes
```

`link` creates `.vercel/project.json` locally; it can also download ignored local environment settings. Never commit that folder or an OIDC token. `vercel.json` defines the build/output, clean static URLs and baseline security headers. `.vercelignore` excludes native exports, caches and local credentials from upload.

Gazebo remains disconnected; no new backend URL is consumed. For optional GA4, configure a real `EXPO_PUBLIC_GA_MEASUREMENT_ID`, disable Enhanced Measurement in the Google stream, rebuild and test opt-in/opt-out under Settings. Submit `/sitemap.xml` to Search Console after publishing. See [Gazebo Integration](GAZEBO_INTEGRATION.md) for the complete architecture and privacy checklist.

To redeploy on another Vercel account, use `vercel link` interactively to choose that account/project. The public subdomain is subject to availability; Vercel assigns a unique URL if the name is taken. Hobby-plan commercial-use restrictions, quotas and custom-domain costs depend on Vercel terms.

For rollback, open the Vercel deployment history and promote the last known-good production deployment. Recheck the API configuration before promotion because it is baked into each deployment. Hash-named bundles keep immutable assets separate between builds.

## 6. EAS Cloud Builds from Windows, Linux, or macOS

EAS builds Android on cloud Linux and iOS on cloud macOS. Local Xcode/Android Studio are not required. An Expo account is required; this workstation was not signed in during delivery.

```bash
npx eas-cli@latest login
npx eas-cli@latest whoami
npx eas-cli@latest init
npx eas-cli@latest build:configure
```

`init` creates/selects your real EAS project and records `extra.eas.projectId` in app config. Review and commit that non-secret configuration change. Do not replace it with a fabricated ID.

Before building, confirm `com.dororolkp.pirate` belongs to your team and is available in the target stores. Changing identifiers after a store release creates a different application.

### Android Test APK

```bash
npx eas-cli@latest build --platform android --profile preview
npx eas-cli@latest build:list --platform android
```

`preview` requests an internally distributed APK. EAS prompts to create/manage a signing keystore when needed. Download the completed APK from its EAS build URL. Allow installation from the trusted source on a test device.

```bash
# Optional Android SDK platform-tools:
adb devices
adb install -r path/to/pirate.apk
```

An APK is installable; an AAB is intended for store distribution. `-r` updates an existing package signed with the same certificate.

### iOS Simulator Build

```bash
npx eas-cli@latest build --platform ios --profile preview
npx eas-cli@latest build:run --platform ios
```

The `preview` iOS profile sets `simulator: true`. Its artifact is a simulator app, **not an IPA for an iPhone**. Build it from Windows if desired, but install/run it on a Mac with a compatible simulator.

### Signed Production AAB and IPA

```bash
npx eas-cli@latest build --platform android --profile production
npx eas-cli@latest build --platform ios --profile production
```

Or `--platform all`. Production increments native build versions using EAS remote version management. Android uses `app-bundle`. iOS needs an Apple Developer team, distribution certificate and provisioning profile; EAS can manage these after authentication. Do not commit downloaded signing keys.

For ad-hoc iPhone distribution, add a separate EAS profile with `distribution: internal` and iOS `simulator: false`, register permitted device UDIDs using `eas device:create`, and build that profile. Apple membership and provisioning requirements still apply.

### Development Client

Install the required package before using the `development` profile:

```bash
npx expo install expo-dev-client
npx eas-cli@latest build --platform android --profile development
npx expo start --dev-client
```

Use `--platform ios` for a provisioned iPhone development client or configure a simulator development profile. Adding native libraries requires a new native build; restarting Metro alone does not add native code.

### What Bundle Export Proves

```bash
npm run build:bundles
```

Generates web bundles and Android/iOS Hermes bytecode under `native-export/`. It proves Metro resolves/transforms the shared application for those platforms. It does **not** compile Swift/Kotlin, validate store signing, produce APK/AAB/IPA, run a native device, or submit to stores.

## 7. Store Submission

### Google Play

1. Create the Play Console application and store listing, privacy policy, data-safety declaration, screenshots and testing track.
2. Configure Play App Signing and retain the correct upload key.
3. Upload the first signed AAB manually; Google requires this before API submissions.
4. Create an authorized Google service account for subsequent submissions; store the JSON key securely outside the repository.
5. Start with an internal testing track, review the build, then promote through the console.

```bash
npx eas-cli@latest submit --platform android --profile production
```

Select the verified build interactively. Avoid `--latest` when multiple team members create builds because it may select the wrong artifact.

### Apple / TestFlight

1. Create the app in App Store Connect using the same bundle identifier.
2. Configure Apple team access and an App Store Connect API key or interactive credentials.
3. Submit the signed production build, selecting the correct App Store Connect app.
4. Wait for processing, then distribute through TestFlight. External testers can require Beta App Review.
5. Complete listing metadata, privacy labels, export-compliance answers and screenshots; manually submit for App Review.

```bash
npx eas-cli@latest submit --platform ios --profile production
```

EAS submission uploads the binary; it **does not automatically publish an App Store release**. `submit.production` intentionally contains no invented store app ID, service account path or Apple team ID.

## 8. Local Native Builds

### Android

Install Android Studio, SDK Platform 37, Build Tools matching Expo/RN requirements, SDK Platform-Tools, an emulator image, and a compatible JDK (use Android Studio's supported JDK and Expo's current build requirements). Set `ANDROID_HOME` to the SDK location and add its `platform-tools` to PATH. Accept SDK licenses.

```bash
java -version
adb version
npx expo run:android
```

`expo run:android` prebuilds native files when absent, runs Gradle and installs a local debug build. It does not create a production-signed store release. If Expo reports a JDK/SDK mismatch, align with the current SDK 58 build image rather than forcing an unsupported Gradle version.

### iOS

Use macOS, Xcode 26.4+, Command Line Tools and Xcode license/setup completion. Expo's local build command handles native generation and CocoaPods installation; follow its prompt if CocoaPods is missing.

```bash
xcodebuild -version
xcode-select -p
npx expo run:ios
```

Windows cannot run Xcode or an iOS simulator. EAS cloud is the supported path here.

## 10. Release Checklist and Troubleshooting

- Run `npm ci`, `npm run check`, `npm run test:e2e`, `npm run build:bundles`, `expo-doctor`, and `npm audit`.
- Confirm demo/live mode, HTTPS API URL, backend availability and robot-side safety approval.
- Confirm no keys, `.env.local`, native signing files or generated exports are staged.
- Check dispatch, cancel acknowledgment, offline guards, manual exclusivity, CSV, reset and routing.
- Test installable native builds on physical Android/iOS devices, including background/resume and share sheets.
- Confirm privacy/support links and store metadata before submission.

| Symptom                                       | Action                                                                                            |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| PowerShell blocks npm.ps1                     | Use `npm.cmd` and `npx.cmd`; do not weaken machine policy blindly                                 |
| Missing optional dependency in Linux `npm ci` | Regenerate lockfile in a clean directory and review it, then verify both OS installs              |
| Port 8081 busy                                | Stop the existing Expo/serve process or choose a separate port                                    |
| Playwright says server already used           | Stop the server or set `TEST_BASE_URL=http://localhost:8081` for an existing exported preview     |
| Device cannot connect to Metro                | Check LAN/firewall or use `--tunnel`                                                              |
| API inaccessible on a phone                   | Use a reachable HTTPS URL; phone localhost is not the development PC                              |
| Dispatch disabled                             | Check connection, heartbeat age, busy/manual status, pending commands and visible API errors      |
| Command outcome unknown                       | Reconcile task acceptance with backend operator; never blindly retry or reload to bypass the lock |
| Native module not found                       | Install SDK-compatible package and rebuild native client                                          |
| TypeScript recursion error with direct tsc    | Run `npm run typecheck`, which supplies the needed stack size                                     |
| EAS says not logged in                        | Run `eas-cli login` locally; never send account passwords/tokens in chat                          |
| Signing/store rejection                       | Review cloud logs, app identifiers, team roles, certificates, privacy and store requirements      |

OTA updates are **not configured** in this MVP. To adopt them, install/configure `expo-updates`, choose runtime-version policy, rebuild clients, and agree release/rollback channels. The EAS profile channel names alone do not enable OTA delivery.
